# 踩坑

每一条都是从手机日志里抠出来的。日志原文照贴，方便你搜到这里。

## 1. 录音一开就停，读到 0 字节

**现象**

```
AudioRecord state=1, sampleRate=16000
AudioRecord recording state=1          ← 应该是 3
AudioRecord.read returned 0
```

**logcat 里的原因**

```
AppOps  : Bad call made by uid 1041. Package "android" does not belong to uid 2000.
AppOps  : Cannot startOperation: non-application UID 2000
AudioPolicyInterfaceImpl: startInput permission denied: recording not allowed for attribution source
        AttributionSourceState{pid: ..., uid: 2000, ..., packageName: android, ...}
```

`getCallDownlinkExtractionAudioRecord` 建 `AudioRecord` 的时候不带 Context，身份取的是 `ActivityThread` 里那个全局的 Application。我们是用 `ActivityThread.systemMain()` 起的，那个 Application 的包名是 `android`，而进程的 uid 是 2000（shell）。系统核对"这个包是不是属于这个 uid"，对不上，拒了。

第二行 `non-application UID 2000` 看着像"shell 身份不许录"，其实不是。它只是把真正的报错盖住了：uid 小于 10000 的，系统就只打这一句。

**修法**（`CallAudioProbe.audioManager()` 里）

新建一个 `Application`，把它的 `mBase` 设成冒充 `com.android.shell` 的 FakeContext，再塞进 `ActivityThread.mInitialApplication`。FakeContext 要重写 `getAttributionSource()`，返回 uid 2000 + 包名 `com.android.shell`。

改完，同一通电话里录满了 10 秒。对方只说了一个"喂"，录音里正好有一秒多的人声，其余是静的，对得上。

## 2. 程序说送完了，对方没听到

**现象**

```
AudioTrack state=1, sampleRate=16000
AudioTrack play state=3
AudioTrack wrote 96000 bytes; waiting for playback
Playback complete: 48000 frames
```

一切正常，返回码 0。电话那头的人说：我这边没声音，是你那部手机自己在响。

**logcat 里的原因**

```
APM_AudioPolicyManager: getOutputForAttrInt() ... Usage: AUDIO_USAGE_CALL_ASSISTANT ... stream=AUDIO_STREAM_MUSIC
        ... device {AUDIO_DEVICE_OUT_EARPIECE, @:} ...
```

系统接口在普通电话这条分支上，只是给这路声音打一个"通话助理"的标签，送到哪里由厂商的音频策略定。这台手机的策略里没有给这个标签单独安排去处，把它当成了普通媒体，通话中的普通媒体走听筒。

**修法**（`preferTelephony()`）

拿到 `AudioTrack` 以后，从 `AudioManager.getDevices(GET_DEVICES_OUTPUTS)` 里找出类型是 `TYPE_TELEPHONY` 的那个输出设备，`track.setPreferredDevice()` 明着点名它。

改完，通话中的 logcat：

```
APM_AudioPolicyManager: getOutputForAttrInt()- ... output 61 selectedDeviceId 11
        device {AUDIO_DEVICE_OUT_TELEPHONY_TX, @:} ... flags 0x80000000
```

`0x80000000` 是 `AUDIO_OUTPUT_FLAG_INCALL_MUSIC`。电话那头："听见了！"

**教训**：这一关机器自己验不出来。日志、返回码、播放进度全是对的。只能让电话那头的人告诉你。

## 3. 怎么知道你的手机有没有这条通道

不用打电话就能看：

```sh
adb shell dumpsys media.audio_policy | grep -iE "telephony_tx|telephony_rx|in_call_music|INCALL_MUSIC"
adb shell dumpsys package com.android.shell | grep -E "CALL_AUDIO_INTERCEPTION|MODIFY_PHONE_STATE|CAPTURE_AUDIO_OUTPUT"
```

我们这台看到的是：有 `telephony_tx`、`telephony_rx` 两个设备口，有一个带 `AUDIO_OUTPUT_FLAG_INCALL_MUSIC` 的 `in_call_music` 混音口，shell 这三项权限都是 `granted=true`。

再跑 `CallAudioProbe route-test`：它建一路普通的声音、点名电话线出口、放半秒静音，打印实际被派到哪个设备。`type=18` 就是电话线。

这些都通过，只说明"路在"。声音真的到没到对方，还是第 2 条那句话：打一通，问人。

## 4. 边录边送能不能同时开

能。`stream` 模式里录音和播放同时开着，一通电话里下行收了三百多万字节、上行送了七十多万字节，没有报错。

## 5. wait-call 模式一跑就崩

```
NullPointerException: Attempt to invoke virtual method
'android.os.TelephonyServiceManager$ServiceRegisterer
 android.os.TelephonyServiceManager.getSubscriptionServiceRegisterer()' on a null object reference
```

原本想在 Java 里自己查通话状态。`systemMain()` 起的进程里电话那套服务没初始化。没修，改成在 shell 里轮询 `dumpsys telephony.registry`。

## 6. 在 adb shell 里按名字杀进程，把自己也杀了

`adb shell 'pkill -f guard.sh; ...'`，这条命令自己的命令行里就有 `guard.sh` 这几个字，于是 pkill 把自己这条 shell 也杀了，电脑这头的 adb 一直挂到超时。用 pid 文件杀。

## 7. iPhone 接通电话时录屏会被掐掉

想把"AI 接电话"录下来给人看：打电话的那部 iPhone 一接通，系统就停了录屏。拿另一台设备对着拍，或者把两边的声音存下来（`bridge.py` 会存在 `turns/` 里）。
